Lektion 6: Webhooks ​

Lernziel ​

Du kennst Webhooks als Alternative zu Long Polling, weißt, was Telegram dafür verlangt, und kannst einen Server schreiben, der Updates entgegennimmt, auf Echtheit prüft und schnell beantwortet. Du meldest den Webhook an, kontrollierst seinen Status und entfernst ihn wieder.

Das Beispiel dieser Lektion läuft nur mit einer öffentlichen HTTPS-Adresse. Du musst es nicht starten, um die Lektion zu verstehen. Die Tests in der Projekt-CI prüfen den Server lokal, ohne Telegram.

Erklärung ​

Zwei Wege zu den Updates. Bisher hat dein Programm Telegram gefragt (getUpdates). Bei einem Webhook dreht sich das um: Du nennst Telegram eine Adresse, und Telegram schickt jedes Update als POST mit dem Update als JSON an diese Adresse.

Long Polling (Lektion 3)Webhook
Wer startet die Verbindung?dein BotTelegram
Was braucht dein Bot?nur Internetzugangeine öffentlich erreichbare HTTPS-Adresse
Verteilungein Programm, eine SchleifeTelegram öffnet bis zu max_connections Verbindungen gleichzeitig (1 bis 100, Standard 40)
Wenn dein Server nicht antwortetnichts geht verloren, Updates wartenTelegram wiederholt die Anfrage und gibt nach einer „angemessenen Zahl von Versuchen" auf
Typischer EinsatzEntwicklung, kleine BotsBots im Dauerbetrieb auf einem Server

Beide Wege schließen sich aus: Solange ein Webhook gesetzt ist, funktioniert getUpdates nicht (Fehler 409, siehe Lektion 3). Um zu Long Polling zurückzukehren, rufst du deleteWebhook auf.

Was Telegram verlangt (Bot-API-Doku und Webhook-Anleitung):

  • HTTPS, immer. Ein Webhook über unverschlüsseltes HTTP ist nicht möglich.
  • TLS 1.2 oder höher und ein Zertifikat, das von einer vertrauten Zertifizierungsstelle stammt. Ein selbst signiertes Zertifikat geht, wenn du es mit dem Parameter certificate hochlädst. Der Name im Zertifikat (CN oder SAN) muss zur Domain passen, und alle Zwischenzertifikate müssen mitgeliefert werden.
  • Port 443, 80, 88 oder 8443. Andere Ports funktionieren nicht.
  • IPv4. IPv6 wird für Webhooks derzeit nicht unterstützt.
  • Willst du den Zugriff auf Telegram beschränken, erlaube die Netze 149.154.160.0/20 und 91.108.4.0/22. Die Bereiche können sich ändern, prüfe die Anleitung, wenn etwas nicht mehr geht.

Anmelden mit setWebhook. Wichtige Parameter:

ParameterBedeutung
urldie HTTPS-Adresse. Ein leerer String entfernt den Webhook.
secret_tokenGeheimnis, das Telegram bei jeder Anfrage im Header X-Telegram-Bot-Api-Secret-Token mitschickt. 1 bis 256 Zeichen aus A-Z, a-z, 0-9, _ und -.
allowed_updatesgewünschte Update-Typen, wie bei getUpdates. Fehlt das Feld, gilt die vorherige Einstellung weiter, sende es deshalb immer mit.
max_connectionsgleichzeitige Verbindungen, 1 bis 100
drop_pending_updatestrue verwirft alles, was bis jetzt aufgelaufen ist
ip_address, certificatefeste IP-Adresse und eigenes Zertifikat

Warum das Geheimnis wichtig ist. Die Adresse deines Webhooks ist eine ganz normale URL. Jeder, der sie kennt (sie taucht in Logs und Proxys auf), kann dir ein POST mit einem erfundenen Update schicken, zum Beispiel eine Nachricht, die angeblich von deinem Administrator kommt. Nur das Geheimnis zeigt, dass die Anfrage von dem Webhook stammt, den du gesetzt hast. Prüfe es bei jeder Anfrage und lehne alles ohne das richtige Geheimnis ab.

Schnell antworten. Telegram wartet auf eine Antwort mit einem Statuscode aus der 2xx-Gruppe. Alles andere und Zeitüberschreitungen führen zu Wiederholungen, dasselbe Update kommt dann noch einmal. Arbeit, die dauert (API-Aufrufe, Datenbank), gehört deshalb nicht in die Anfrage: Der Server reiht das Update ein, antwortet sofort mit 200 und verarbeitet es dahinter. Ist die Warteschlange voll, antwortet er mit 503, und Telegram versucht es später wieder.

Die Antwort als API-Aufruf. Du kannst in der Antwort auf den Webhook selbst einen Methodenaufruf mitgeben (Feld method plus die Parameter). Das spart einen Aufruf, aber du erfährst weder, ob er geklappt hat, noch das Ergebnis. Das Beispiel nutzt diesen Weg nicht.

Der Status mit getWebhookInfo. Die erste Anlaufstelle, wenn keine Updates ankommen: url, pending_update_count (wie viele Updates warten), last_error_date und last_error_message (der letzte Fehler beim Zustellen, etwa „Connection refused"). Verwendet dein Bot getUpdates, ist url leer.

Wo läuft der Server? TLS übernimmt in der Praxis ein Reverse Proxy (z. B. nginx oder Caddy) vor deinem Programm, oder bei der Entwicklung ein Tunnel, der eine öffentliche HTTPS-Adresse auf deinen Rechner leitet. Das Beispiel spricht deshalb nur HTTP und erwartet, dass davor TLS endet.

Methoden dieser Lektion

  • setWebhook (Updates empfangen)
  • deleteWebhook (Updates empfangen)
  • getWebhookInfo (Updates empfangen)

curl ​

bash
API="https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN"

# Webhook setzen (Adresse und Geheimnis ersetzen)
curl "$API/setWebhook" -H "Content-Type: application/json" \
  -d '{"url":"https://beispiel.example/telegram","secret_token":"GeheimesWort_123","allowed_updates":["message"]}'

# Status ansehen
curl "$API/getWebhookInfo"

# Webhook entfernen, danach geht getUpdates wieder
curl "$API/deleteWebhook"

Java ​

Das Modul examples/06-webhooks hat drei Teile: den Server, die Anmeldung bei Telegram und den Bot, der beides verbindet.

Der Server. WebhookServer basiert auf dem HttpServer des JDK. Die Reihenfolge der Prüfungen ist wichtig: erst Methode, dann Geheimnis, dann Größe und JSON, und erst dann wird das Update eingereiht. Geantwortet wird mit 405 (nur POST), 403 (falsches Geheimnis), 413 (zu groß), 400 (kein Update), 503 (überlastet) oder 200:

java
private void anfrage(HttpExchange austausch) throws IOException {
    try (austausch) {
        if (!austausch.getRequestMethod().equals("POST")) {
            austausch.getResponseHeaders().set("Allow", "POST");
            antworten(austausch, 405);
            return;
        }
        // Wer das Geheimnis nicht kennt, hat dieses Update nicht von Telegram bekommen.
        if (!gleich(secret, austausch.getRequestHeaders().getFirst(SECRET_HEADER))) {
            antworten(austausch, 403);
            return;
        }
        byte[] koerper = austausch.getRequestBody().readNBytes(MAX_BYTES + 1);
        if (koerper.length > MAX_BYTES) {
            antworten(austausch, 413);
            return;
        }
        JsonNode update;
        try {
            update = JSON.readTree(koerper);
        } catch (IOException e) {
            antworten(austausch, 400);
            return;
        }
        if (update == null || !update.has("update_id")) {
            antworten(austausch, 400);
            return;
        }
        try {
            // Nur einreihen und sofort antworten. Telegram wiederholt Anfragen, die nicht mit 2xx beantwortet
            // werden, die eigentliche Arbeit darf also nicht in der Anfrage stattfinden.
            verarbeitung.execute(() -> verarbeiten(update));
        } catch (RejectedExecutionException e) {
            antworten(austausch, 503);
            return;
        }
        antworten(austausch, 200);
    }
}

Das Geheimnis wird zeitkonstant verglichen. Ein einfaches equals bricht beim ersten falschen Zeichen ab, und aus der Antwortzeit ließe sich das Geheimnis Zeichen für Zeichen erraten:

java
/** Zeitkonstanter Vergleich: Die Dauer verrät nicht, wie viele Zeichen des Geheimnisses schon stimmen. */
static boolean gleich(byte[] erwartet, String erhalten) {
    byte[] gesendet = erhalten == null ? new byte[0] : erhalten.getBytes(StandardCharsets.UTF_8);
    return MessageDigest.isEqual(erwartet, gesendet);
}

Die Verarbeitung läuft hinter der Antwort in einem Thread mit einer Warteschlange von 1000 Updates. So werden Updates der Reihe nach bearbeitet. Bei parallelen Verbindungen liefert Telegram ohnehin nicht garantiert in der Reihenfolge der update_id.

Anmelden, Status, Entfernen. Das Geheimnis erzeugt neuesGeheimnis() aus 32 Zufallsbytes in genau dem Zeichensatz, den Telegram erlaubt:

java
/**
 * Teilt Telegram mit, wohin es Updates schicken soll.
 *
 * @param url             öffentliche HTTPS-Adresse, Port 443, 80, 88 oder 8443
 * @param secret          kommt bei jeder Anfrage im Header {@code X-Telegram-Bot-Api-Secret-Token} zurück
 * @param allowedUpdates  gewünschte Update-Typen, leer heißt "Standard"
 * @param verwerfen       {@code true} verwirft Updates, die sich bis jetzt angesammelt haben
 */
public static void setzen(TelegramClient client, String url, String secret, List<String> allowedUpdates,
        boolean verwerfen) throws IOException, InterruptedException {
    ObjectNode parameter = TelegramClient.parameter().put("url", url).put("secret_token", secret);
    // Immer mitsenden: Fehlt das Feld, gilt die vorherige Einstellung weiter (wie bei getUpdates).
    ArrayNode liste = parameter.putArray("allowed_updates");
    allowedUpdates.forEach(liste::add);
    if (verwerfen) {
        parameter.put("drop_pending_updates", true);
    }
    client.aufrufen("setWebhook", parameter);
}
java
/** Der Status laut Telegram: {@code url}, {@code pending_update_count}, {@code last_error_message} u. a. */
public static JsonNode info(TelegramClient client) throws IOException, InterruptedException {
    return client.aufrufen("getWebhookInfo");
}

/** Entfernt den Webhook. Erst danach funktioniert {@code getUpdates} wieder. */
public static void loeschen(TelegramClient client, boolean verwerfen) throws IOException, InterruptedException {
    ObjectNode parameter = TelegramClient.parameter();
    if (verwerfen) {
        parameter.put("drop_pending_updates", true);
    }
    client.aufrufen("deleteWebhook", parameter);
}
java
/** 32 zufällige Bytes als 43 Zeichen aus A-Z, a-z, 0-9, _ und -, genau das, was Telegram erlaubt. */
public static String neuesGeheimnis() {
    byte[] zufall = new byte[32];
    ZUFALL.nextBytes(zufall);
    return Base64.getUrlEncoder().withoutPadding().encodeToString(zufall);
}

Der Bot. WebhookBot liest die Konfiguration aus Umgebungsvariablen, startet erst den Server und meldet ihn dann an, damit keine Updates kommen, bevor jemand zuhört. Der Handler spiegelt Text wie der Echo-Bot aus dem Quick-Start:

java
public static void main(String[] args) throws Exception {
    String url = System.getenv("WEBHOOK_URL");
    if (url == null || !url.startsWith("https://")) {
        System.err.println("WEBHOOK_URL fehlt oder ist nicht https://, z. B. https://beispiel.example/telegram");
        System.exit(2);
    }
    int port = Integer.parseInt(System.getenv().getOrDefault("PORT", "8080"));
    String secret = System.getenv().getOrDefault("WEBHOOK_SECRET", Webhook.neuesGeheimnis());
    TelegramClient client = TelegramClient.ausUmgebung();

    // Erst den Server starten, dann Telegram Bescheid geben: Sonst kommen Updates, bevor jemand zuhört.
    String pfad = URI.create(url).getPath().isEmpty() ? "/" : URI.create(url).getPath();
    WebhookServer server = WebhookServer.starten(port, pfad, secret, update -> antworten(client, update));
    Webhook.setzen(client, url, secret, List.of("message"), false);
    System.out.println("Webhook läuft auf Port " + port + ", Pfad " + pfad + ". Strg+C beendet.");
    Thread.currentThread().join();
    server.close();
}
java
/** Wird für jedes Update aufgerufen: spiegelt den Text einer Nachricht. */
static void antworten(TelegramClient client, JsonNode update) {
    JsonNode nachricht = update.path("message");
    if (!nachricht.has("text")) {
        return;
    }
    try {
        client.aufrufen("sendMessage", TelegramClient.parameter()
                .put("chat_id", nachricht.path("chat").path("id").asLong())
                .put("text", nachricht.get("text").asText()));
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}

Optional: mit einem Tunnel selbst ausprobieren

Dafür brauchst du cloudflared (Cloudflare Tunnel, der Quick-Tunnel braucht kein Konto). Was das Programm macht und wo du es bekommst, steht auf der Seite Werkzeuge. Einen solchen Tunnel nutzt auch die Lektion zu Mini Apps.

  1. In einem Terminal: cloudflared tunnel --url http://localhost:8080. Die Ausgabe nennt eine Adresse wie https://<zufall>.trycloudflare.com.
  2. In einem zweiten Terminal den Bot starten, mit dieser Adresse und einem Pfad:
    bash
    WEBHOOK_URL=https://<zufall>.trycloudflare.com/telegram \
  ./mvnw -q compile exec:java -pl examples/06-webhooks -am \
  -Dexec.mainClass=telegram.lernen.webhooks.WebhookBot
  3. Schreibe deinem Bot. Er spiegelt den Text. WebhookVerwalten info zeigt pending_update_count und Fehler.
  4. Danach den Webhook mit WebhookVerwalten loeschen entfernen. Sonst scheitern alle Beispiele mit getUpdates mit einem 409.

Dieser Weg hängt von deiner Umgebung ab (Firewall, installierte Software) und ist nicht Teil der Tests.

Übung ​

Eine Leseaufgabe: Beantworte die Fragen anhand des Codes und der Erklärung oben.

  1. Warum reicht es nicht, die Webhook-Adresse geheim zu halten?
  2. Warum antwortet der Server sofort mit 200, statt die Antwort erst nach der Verarbeitung zu senden?
  3. Was passiert, wenn mehr als 1000 Updates auf Verarbeitung warten?
  4. Du startest PollingBot aus Lektion 3, während ein Webhook gesetzt ist. Was siehst du, und was tust du?
Lösung
  1. Die Adresse ist eine normale URL und taucht in Logs, Proxys und Fehlermeldungen auf. Wer sie kennt, kann gefälschte Updates schicken. Nur das Geheimnis im Header X-Telegram-Bot-Api-Secret-Token zeigt, dass die Anfrage von dem Webhook stammt, den du gesetzt hast.
  2. Telegram wiederholt Anfragen, die nicht rechtzeitig mit 2xx beantwortet werden. Dauert die Verarbeitung (API-Aufrufe, Datenbank), käme dasselbe Update mehrfach an. Deshalb reiht der Server es nur ein und antwortet sofort.
  3. Die Warteschlange ist voll, execute wirft eine RejectedExecutionException, und der Server antwortet mit 503. Telegram versucht es später wieder. Das schützt den Speicher des Servers.
  4. getUpdates scheitert mit dem Fehler 409, die Schleife aus Lektion 3 beendet sich mit einer TelegramException. Entferne den Webhook mit deleteWebhook (z. B. WebhookVerwalten loeschen) und starte PollingBot neu.
